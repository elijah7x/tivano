# 夜间性能专项 · 2026-10-18

## 结论

用户感受到的“开始卡以后，连设置页切换、鼠标移动热区都卡”，根因已经测到：**有会话流式输出时，主线程几乎没有空闲**。不论聊天是否被设置页盖住，主线程都在为“正在写的那一段”反复重建可选文字的 TextKit 布局。SwiftUI 的 `.textSelection(.enabled)` 在文字每变一次时，都会从头重建整段的 `NSTextLayoutManager`，所以每来一个 token 都要重算一遍，越长越慢。

修复后，在同一个三会话流式压测里：

| 指标（同一机器、同一压测，3 次 A/B 交替） | 修复前 A | 修复后 B | 变化 |
| --- | --- | --- | --- |
| 设置页盖住聊天时，主线程心跳间隔中位数 | 42–48 ms | 5.1 ms | 回到空闲水平（目标 4 ms 睡眠） |
| 同上，进程 CPU（5 秒窗口） | 4.78–4.94 s | 1.92–2.23 s | −55% ～ −61% |
| 同上，超过 16.7 ms 的心跳占比 | 91/134 ～ 97/145（约 65%） | 34/764 ～ 83/736（约 10%） | |
| 聊天可见时，主线程心跳间隔中位数 | 70–72 ms | 5.1 ms | |
| 同上，进程 CPU（5 秒窗口） | 4.55–4.75 s | 2.13–2.20 s | −53% |
| 同上，心跳 p95 | 101–105 ms | 17.7–19.6 ms | |

心跳间隔衡量的是“主线程多久才能回来处理下一件事”，也就是点击和悬停要排队多久，不是帧率。修复前，压测期间每次点击或悬停平均要等 45–70 ms 才开始处理；修复后约 5 ms。

## 怎么测的

- 新增仅 Debug 的探针 `SettingsInteractionProbe`（`--website-captures <dir> --settings-interaction-probe`）。它在隔离的 CaptureRun 数据里运行，不碰真实数据，也不调用 provider。流程分五段：空闲切换所有设置页 3 轮；空闲心跳；三会话流式负载下再切 3 轮；设置页盖住聊天时的心跳；回到聊天时的心跳。结果写入 `settings-interaction.json`。负载复用 `HeavyLoadProbe` 的三会话流式文字回放，抽成了 `startStationaryTextLoad`。
- A 是 HEAD 的产品代码加同一个探针；B 是当前工作区。两者都是 `-O` 的 Debug 构建，A/B 交替运行。脚本在 `build.noindex/scripts/`（`build_ab.sh`、`run_settings_probe.py`、`summarize.py`、`profile_probe.py`、`inclusive.py`）。数据在 `build.noindex/settings-probe/`。
- 早上解锁后，在正常前台条件下（不加任何诊断开关）又跑了 3 组 A/B（`run5-foreground`）：盖住聊天时 A 44–64 ms / 4.8–5.1 s，B 5.1 ms / 1.75–2.6 s；聊天可见时 A 84–103 ms / 4.6–5.1 s，B 5.1 ms / 2.8–3.2 s（前台多了真实上屏绘制，CPU 降约 40%）。结论与锁屏下一致。
- 夜里屏幕被锁，窗口无法成为前台。为此给探针加了诊断开关 `--allow-locked-screen`，并用 `-NSAppSleepDisabled YES`（仅作启动参数，不写偏好）避免 App Nap 降频。锁屏前用完整前台条件跑过一组（`run1`），A 的数值与锁屏下一致：盖住时 48 ms / 4.95 s，聊天可见时 83–85 ms / 4.6–4.75 s。**B 尚未在解锁的前台条件下复测**。
- 用 `sample` 抓主线程调用栈定位热点（会扰动计时，只看占比，不看耗时）。

## 定位到的热点

1. **流式段落的可选文字布局**：修复前，聊天可见时主线程 46%、被盖住时 33% 的样本落在 `TextSelection.Configuration.dataSource → configureTextLayoutManager → NSTextLayoutManager ensureLayoutForRange`。
2. **每个 token 都从头重建富文本**：`RichLink.prettyAttributed` → `build` → `autolinkedBareDomains`，其中裸域名识别对整段跑正则，并按字符从头偏移切片；`VeiledText.ingest` 每次复制整段字符索引数组。
3. **设置页切换**：每切一页 30–130 ms，冷 CPU（空闲时点击）约是负载下的 2 倍（降频影响）。时间主要花在 SwiftUI 新建页面并布局（Stack/Frame 尺寸计算），文字测量约 6%。Providers 最贵（空闲约 130 ms），Models、MCP、Hydra 次之（约 100 ms），Archive 最便宜（约 30 ms）。

## 采用的改动

关键修复（有实测）：

- **正在写的段落暂不启用文字选择**（Vera，`MarkdownView.swift` 的 `MarkdownBlockSelection`、`StreamVeil.swift` 的 `VeiledText`）。条件是“仍在流式”或“淡入尚未结束”；淡入结束、文字完全静止后才打开选择，这次切换是一次性的、看不见的。已完成的消息和历史消息照常立刻可选。淡入状态位于切换分支之外，不会重放或跳变。
  - 像素验证：`TextParityProbe` 在 A/B 上各渲染 48 张（明暗、两种宽度、两种字号、中文、阿拉伯文、emoji、组合字符、粗斜体、列表、引用），**48/48 逐像素一致**（`build.noindex/parity/`）。
- **富文本重建减量**（Mira）：裸域名识别加了不会误判的预筛，没有真正可链接的域名时整段直通，切片改为一次遍历；`build` 在无链接时直接返回；`VeiledText` 改为只给新增的尾部补算字符边界。
  - 等价验证：把新旧 `RichLink.build` 抽成独立程序，跑 8000 个随机样本（含流式前缀），**输出（字符、属性、链接）0 差异**；字符边界增量算法与全量重算比对 61,710 步，0 差异（含 ZWJ、国旗、肤色、组合音标、天城文连字）。
  - 在本压测中，这一项没有在 CPU 上测出额外下降（负载已经不再占满主线程），只有心跳 p95 略降。属于降低最坏情况的保险，不报收益。

前两轮的广度优化（代码审阅保证等价，未单独测出收益）：

- 设置页：页面外壳和侧栏行只刷新变化的部分；服务商区块只观察自己的状态；固定选项列表改为静态缓存；Models 搜索每次按键只扫一遍；测量写入加 0.5 pt 容差；其余各页（MCP、Hydra、快捷键、关于、壁纸、Token 热力图）同样处理。
- 折叠的服务商卡片不再构建和测量其内容（`ChromeReveal`），展开和收起动画保持原样。
- 服务商注册表：值没变就不通知界面，批量更新合并成一次通知。
- 公共控件（侧栏行、按钮、选择器、分段控件）：悬停只重绘背景层，悬停状态只在变化时写入。
- 被设置页或语音界面盖住时，闪光、强度滑条特效、通话计时暂停；后台预构建其他会话也暂停。
- 侧栏、命令面板、时间线分组：去掉若干 O(n²) 和重复扫描；侧栏位置缓存利用 `threadsRevision`（所有线程写入都会递增它，已核对）。
- 附件预览：文件存在性和大小缓存 2 秒，**只缓存“存在”的结果**，新生成的文件下一次渲染就能出现。

## 试过但撤回的

- **盖住时把聊天列移出窗口**：绘制确实停了，但 SwiftUI 对脱离窗口的视图仍会求值和布局，CPU 不降（1.94 s 对 1.94 s）；同时有 onAppear/onDisappear 和任务重启的风险。已撤回。

## 主负责人做的修正

- 命令面板改动编译失败（惰性链推断不出类型），改为普通过滤。
- 附件元数据缓存原本把工具图片路径的永久缓存改成了 2 秒过期，反而更慢；还会缓存“文件不存在”，导致工具刚生成的图片可能一直不显示。已恢复永久缓存，并且只缓存正面结果。
- `VeiledText` 下标转换原本强制解包，改为安全回退。
- 若干缩进和空行整理。

用合成鼠标/键盘事件实际操作隔离的 Debug 构建（探针新增 `--hold-for-interaction`，跑完后保留窗口），并截图查看：

- 流式结束后拖选两行文字并 Cmd+C：高亮正常，剪贴板内容正确（测试前后已恢复你的剪贴板）。

- 命令面板：打开、方向键选择、搜索“final”命中两条、无匹配提示均正常。
- 模型页：拖拽排序（移到末尾再拖回）、搜索“flash”分组结果均正常。
- A/B 同一脚本逐像素对比：设置侧栏悬停、设置行悬停、标题栏按钮悬停、服务商页、外观页全部一致；聊天侧栏唯一差别是三个压测会话的先后顺序（它们同时结束，按更新时间排序，顺序随运行时机变化，同一 B 版本两次启动也不同）。

## 仍需注意
- 折叠后再展开服务商卡片，卡片里显示的登录错误提示会被清空（子视图状态随卸载丢失）。这是唯一已知的行为差异，影响很小，需要你确认能否接受。
- 这个压测是三段长文本持续流式，属于偏重的场景；真实负载下的收益比例会不同。

## 下一步建议

1. 设置页切换本身仍要 30–130 ms，主要是 SwiftUI 新建整页的固有开销。可选方向：页面内部改为按需构建（需逐页核对状态是否会丢）；或者缓存最近访问的页面（会带来后台更新开销，需要测）。
2. 流式期间剩余的主线程工作主要是可见文字的测量和 CPU 绘制，属于正常显示成本；进一步优化需要动到渲染路径（此前评估的原生文本路由收益大，但有字形差异，未采用）。
3. 保存快照、Hydra 看门狗等非界面工作，见 `settings-and-interaction-audit.md` 第 5 节，建议用同一探针加长时间窗口再测。
